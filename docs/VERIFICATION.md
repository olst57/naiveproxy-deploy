# 验证记录与计划

本文件收录本项目的验证证据：真机端到端结果、静态/模拟验证范围、以及尚未执行的部分。
README 面向使用者，本文件面向「凭什么相信它能跑」的追问。

## 真机验证结果（2026-10-13，已完成）

在真实 VPS 上跑完了端到端验证（Debian 13, 1 vCPU / 958 MB, 域名以 `your.domain.com` 代指）。
**这是本项目第一次在真 Linux 上执行** —— 结果值得单独记：静态验证全绿的情况下，
仍然一次抓出 **3 个真 bug**，而当时已有的全部断言（数量见 `--self-test` 自报）、shellcheck 和两轮独立评审全都没看见。

### 真机才暴露的 3 个 bug

| # | 问题 | 为什么静态验证看不见 |
| --- | --- | --- |
| 1 | **apt 包名写错**：脚本装 `xz`，但 Debian 系里包名是 `xz-utils`（而 `/usr/bin/xz` 本来就装好了）。整个部署在阶段 1 就失败 | 只存在于真实 apt 的包索引里。断言和 shellcheck 都不会知道 Debian 怎么命名包 |
| 2 | **致命**：阶段 4 用 root 跑 `caddy validate`，caddy 在校验时会初始化 logger，于是把 `access.log` 建成了 `root:root 0600`；阶段 6 服务以 `caddy` 用户运行，**打不开自己的日志文件**，exit 1 并陷入崩溃重启（实测重启 29 次）。阶段 3 的 `chown` 早于这次创建，救不了 | 这是 root 校验与服务用户权限之间的**时序耦合**，纯静态推理极难发现。必须真跑才会撞上 |

> 修复：新增 `ensure_log_dir_owner()`，在启动服务前再修一次属主，并给日志目录设 `setgid 2755`，
> 让之后新建的日志文件自动继承 caddy 组。
> 顺带：`install_deps` 改成**只装确实缺的命令**，并按发行版映射包名 —— 依赖都齐时不再因为包管理器报错而失败。

| # | 问题 | 为什么静态验证看不见 |
| --- | --- | --- |
| 3 | **验证本身是坏的**：阶段 7 用 `127.0.0.1` 当代理地址去测转发。curl 会拿代理地址当 **TLS SNI**，而证书只对域名有效 → SNI 不匹配，TLS 在认证之前就失败（`tlsv1 alert internal error`）。结果：**即使服务完全正常，验证也永远报失败** | 只有真的走到 TLS 握手才会暴露。而且这条和我上一轮修的"假通过"正好相反 —— 那个是**假通过**，这个是**假失败** |

> 修复：代理测试改用真实域名做 SNI；域名在本机解析不通时临时借一行 `/etc/hosts`，
> 退出时精确删掉那一行（已实测无残留）。

## 真机验证计划（主路径部分已执行，见上）

补充说明：**主路径（x86_64 Debian）已按下面的方案在真实 VPS 上执行完毕**（见上一节）。
开发机是 Windows，没有 docker、没有 WSL、没有 Linux 容器，所以**以下这些仍属高置信推断而非已验证**：

- Alpine + openrc 整条路径从未端到端执行（`reload()` 已补但没实测）
- arm64 走 `--build-from-source`（已推理出大概率失败：上游无 arm64 资产 + 未 pin 版本 + 发行版 Go 过旧）
- 失败注入矩阵（故意占住 443、破坏状态文件、伪造域名不解析、打断下载）—— 每一条都要验证
  「输出非空 + 含阶段编号 + 建议命令可执行」

已经规划好一份可照做的验证方案，最小可行集是 **1 台机器 + 1 次重装**：

1. **主路径**（x86_64 Debian/Ubuntu）：7 阶段端到端、真 naive 客户端回环验证、四条运维路径、连续 5 次重跑看幂等
   —— **已执行**（见上）；四条运维路径中 `--uninstall --purge` 已实测
2. **失败注入**：故意占住 443、破坏状态文件、伪造域名不解析、打断下载 —— 每一条都验证"输出非空 + 含阶段编号 + 建议命令可执行"
3. **原地重装成 Alpine**：覆盖 openrc + busybox + 无 `ss` 路径
4. arm64 **不单独买机器** —— 除非第 2 步的推理被推翻

停止条件是「**每一条"通过"的判据都必须在故意做错时变红**」。其中第 1 条（代理判据）和第 3 条（端口）
在 v2.2.0 之前是**不会变红的** —— 那正是这一轮修掉的东西。

## 已验证范围

- `bash -n` 语法检查通过；`shellcheck -x`（default 与 style 级别）零告警
- `--self-test` 全部通过（数量由脚本自报；v2.6.0 为 **406 项** 通过 / 0 失败），但在真机上仍漏掉了 3 个 bug（见上「真机验证结果」）。包含结构性断言（每条交互设计一个）、行为级断言（状态文件往返一致性、注入抵抗、渲染器静默性、退出码真实传递），以及"把 bug 放回去就变红"的证伪验证
- **退出码 2（v2.6.0 新增）**：真起子进程跑 `main` 验证三种情形的真实退出码 ——
  有警告时退 2、`--skip-verify` 时退 0、全过时退 0；并复核「退出 2 时摘要（含密码）已打印」。
  判定位置（`print_summary` 之后）与 `verify_deployment` 无 `exit`/`die` 各有结构性断言。
  证伪实验 5 条（删判定 / 挪判定 / 塞进 verify_deployment / 改交握项为 `return 1` / 条件写反），
  全部被抓红。其中「改交握项」一条**暴露并修掉了一条假绿断言**（见 CHANGELOG `[2.6.0]`）
- 入口行为实测：无参数 → 引导页（exit 0）；缺 `--domain`/`--email` → 报缺参；非 root 安装 → 给可复制的 sudo 命令；未知参数 → exit 1
- `--check` 实测：无需 root、不改动系统、密码位置显示占位符、不打印任何真实密码形态
- 用官方 caddy **2.11.7**（与 naive fork 同基线）实测校验渲染出的配置：剥离仅依赖 naive 构建的 `order forward_proxy` 与 `forward_proxy` 块之后，其余全部（全局块、日志轮转、`exclude`、站点地址、`tls`、`encode`、`file_server`）判定为 **Valid configuration**
- 渲染器输出与 `caddy fmt` 输出**逐字节一致**
- `--ascii` 模式实测：不出现任何 UTF-8 标记
- 注入链实测：恶意邮箱被校验拒绝；手工构造的含 payload 状态文件在解析时**不会执行**任何命令，且被再校验拦下；换行注入（曾可绕过 `^…$` 锚点）被拒绝
- 渲染器静默性实测：不带引号的 heredoc 里若有反引号会被当命令替换执行（开发过程中真的踩到过），现有断言会捕捉到
- **端口语义实测**（用官方 caddy 2.11.7 的 `adapt`）：`:8443, d.com` → 监听 `[:443, :8443]`；`:8443, d.com:8443` → 只监听 `[:8443]`。
  同时确认带 `:port` 前缀时路由**不含 host matcher**（这是 forward_proxy 需要的），而只写域名会生成 `{"match":{"host":[...]}}`
- **下载校验实测**：从 GitHub API 取到的 sha256 与真实下载**逐字节一致**
- **`fn_body` 确定性验证**：改用 heredoc 感知后，能正确穿过渲染器里的列首 `}` 取到完整函数体
