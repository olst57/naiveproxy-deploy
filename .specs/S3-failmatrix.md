# 任务：失败注入矩阵 —— 验证脚本失败时的行为是否诚实

## 绝对不要做（红线）

1. **禁止碰生产服务器** `root@82.139.194.92` —— 上面跑着线上代理，且有明天 16:14 待触发的证书签发 timer。一切测试只在 CI 容器里跑。
2. **禁止在本机（Windows）跑部署脚本** —— 会真的去改系统。只许在 CI 容器的隔离环境里跑。
3. **禁止并行跑自检** —— 单轮 78 秒 × N 并发会打满 CPU。一次只跑一个。
4. **禁止修改现有 393 条断言的任何一行** —— 只能新增。
5. **禁止生成整份脚本副本做实验**。
6. **禁止提交、禁止 push**。
7. **禁止美化结论** —— 脚本在失败场景下行为不对，就如实写"不对"。这个项目最恨"跑了但报绿"。

## 背景（≤5 行）

脚本有 7 个阶段：`安装系统依赖 / 安装 Caddy 二进制 / 创建运行用户与目录 / 写入 Caddyfile / 布置伪装站点 / 安装并启动服务 / 验证部署`。
`trap cleanup EXIT` 只清临时文件，**没有回滚逻辑**。
失败注入矩阵**从没做过** —— 不知道每个阶段失败时脚本会不会留下烂摊子、会不会假报成功。

## 要做（编号）

1. 新建 `.github/workflows/failure-injection.yml`，在容器里逐个注入失败，看脚本行为。
2. **注入点**（每阶段挑一个真实可注入的）：
   - 阶段 1：让包管理器失败（如把 `apt`/`apk` 换成不存在的路径）
   - 阶段 2：让 Caddy 下载/校验失败（如改坏下载 URL 或校验和）
   - 阶段 3：让 `useradd`/目录创建失败（如先占住目录名）
   - 阶段 4：让 Caddyfile 写入失败（如目标目录只读）
   - 阶段 5：让伪装站点布置失败
   - 阶段 6：让服务启动失败（如占住 443 端口）
   - 阶段 7：让验证失败（如伪造一个错的证书）
3. **每个注入点记录 4 件事**：
   - ① 脚本退出码（**必须非 0** —— 若为 0 就是严重 bug）
   - ② 有没有打印清晰错误信息（不是静默死掉）
   - ③ 留下什么残留（文件/用户/服务/端口占用）
   - ④ 重跑能不能恢复
4. 输出一张矩阵表：`阶段 | 注入方式 | 退出码 | 有错误信息 | 残留 | 可重跑`。
5. **发现的问题**逐条列出（不要只报喜）。

## 验收（必须贴实际输出）

```bash

#   1. workflow 文件内容
#   2. 完整的失败注入矩阵表（7 行）
#   3. 每行背后的实际命令与输出片段
#   4. 发现的 bug 列表（若无可写"未发现"）
```

- 判据 2：每行都有**实测退出码**（不是推测）
- 判据 3：退出码为 0 的行必须被标为 bug
- 判据 4：残留与可重跑都是**实查结果**
